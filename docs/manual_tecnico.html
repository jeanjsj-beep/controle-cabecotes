1. Stack Tecnológica e Linguagens Utilizadas

Arquitetura de Software

O sistema SCRC foi projetado sob uma arquitetura Full-Stack Stateless Serverless-First, desacoplando a interface SPA (Single Page Application) da API RESTful em Python através de contratos JSON validados por schemas estritos. Essa escolha garante zero dependência de disco efêmero em nuvem e baixa latência tanto em redes locais quanto em execução distribuída na Vercel.

Camada Linguagem / Tecnologia Papel Arquitetural e Justificativa de Engenharia
Backend API Python 3.12+
FastAPI >= 0.115.0		 Framework ASGI de alta performance baseado em Starlette, com injeção de dependências nativa (usada para sessões de banco e RBAC) e serialização assíncrona.
Validação de Dados Pydantic v2 >= 2.9.0 Validação estrita de payloads de entrada/saída em Rust-core, prevenindo Mass Assignment, coerção indevida de tipos e payloads malformados.
ORM & Persistência SQLAlchemy >= 2.0.35 Mapeamento Objeto-Relacional com queries 100% parametrizadas (proteção nativa contra SQL Injection) e suporte híbrido PostgreSQL / SQLite.

psycopg2-binary >= 2.9.9		 O driver pg8000 (100% puro Python) garante compatibilidade total em containers AWS Lambda / Vercel Linux sem depender de bibliotecas C dinâmicas (libpq).

2.1. Soluções de Engenharia para Ambientes Serverless (Vercel + Supabase)

  • Normalização Automática de DATABASE_URL em database.py: Como funções Serverless na Vercel operam em rede IPv4 e o host direto do Supabase (db.<ref>.supabase.co:5432) utiliza IPv6 exclusivo, o módulo database.py reescreve automaticamente conexões diretas para o Supabase Transaction Pooler IPv4 (aws-1-sa-east-1.pooler.supabase.com:6543 com usuário postgres.<ref>) e converte o dialeto para postgresql+pg8000:// com NullPool.
  • Armazenamento de Fotos no Próprio Banco (Stateless Storage): Em ambientes Serverless o sistema de arquivos local é efêmero e somente-leitura. Por isso, o endpoint POST /api/upload-foto armazena o binário validado diretamente na tabela fotos_armazenadas (em Base64) e o serve com cache imutável em GET /uploads/{filename}.

4. Máquina de Estados Finitos (FSM) e Regras de Negócio

Regras de Domínio

4.1. Roteamento Dinâmico de Etapas (avancar_proxima_etapa)

Em backend/app/routers/etapas.py, a transição entre postos não é rígida; ela consulta os atributos booleanos requer_* configurados na Triagem do cabeçote. A ordem canônica avaliada é:

ORDEM_ETAPAS = [
    ("LAVAGEM",       True),                        # Sempre executada após a Triagem
    ("JATEAMENTO",    cab.requer_jateamento),
    ("ESTANQUEIDADE", cab.requer_estanqueidade),
    ("FACEAMENTO",    cab.requer_faceamento),
    ("LAPIDACAO",     cab.requer_lapidacao),
    ("MONTAGEM",      cab.requer_montagem),
    ("QUALIDADE",     cab.requer_qualidade),        # Gera e persiste o Relatório Individual JSON/PDF
    ("PINTURA",       cab.requer_pintura),
] -> Finaliza em "PRONTO" (ou "CONDENADO" se reprovar na Estanqueidade)

4.2. Regra de Retrabalho em 2 Níveis na Lapidação & Vácuo

  • Aprovação (APR): Limpa o status de retrabalho e avança a peça para MONTAGEM.
  • 1ª Reprovação no Vácuo (REP com tentativas == 1): Mantém o cabeçote na etapa LAPIDACAO e define lapidacao_status_retrabalho = "TROCAR_VALVULA".
  • 2ª+ Reprovação no Vácuo (REP com tentativas >= 2): Mantém o cabeçote em LAPIDACAO e escala a exigência para lapidacao_status_retrabalho = "TROCAR_SEDE".

5. Arquitetura de Segurança: Especificação das 20 Verificações

DevSecOps & OWASP

O sistema implementa 20 camadas de proteção ativa no backend (main.py e routers/auth.py), no banco de dados (Supabase PostgreSQL) e no cliente SPA (app.js):

# Controle de Segurança Implementação Técnica e Mecanismo de Proteção
01 HTTPS & HSTS Middleware inspeciona X-Forwarded-Proto em produção e força redirecionamento 307 Temporary Redirect para https://, além de injetar Strict-Transport-Security: max-age=63072000; includeSubDomains; preload.
02 CORS Restrito CORSMiddleware configurado com lista explícita de origens confiáveis (produção Vercel, localhost e SCRC_CORS_ORIGINS), restringindo métodos e cabeçalhos permitidos.
03 Senhas com Hash Derivação hashlib.pbkdf2_hmac('sha256', password, salt, 200000) com salt aleatório de 16 bytes (128 bits) por usuário e verificação em tempo constante via hmac.compare_digest(). Política exige 8+ caracteres, maiúscula, minúscula, dígito e símbolo.
04 Cookies Seguros No login, o servidor emite o cookie scrc_session com flags HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=86400, impedindo leitura via JavaScript malicioso.
05 Proteção de Secrets Chaves de assinatura e criptografia derivadas via KDF (PBKDF2) a partir de variáveis de ambiente (SCRC_AUTH_SECRET, SCRC_ENCRYPTION_KEY). Documentação /docs, /redoc e /openapi.json desativadas por padrão em produção.
06 Controle de Acesso (RBAC) Dependências FastAPI requer_permissao(modulo) e requer_admin aplicadas em todas as rotas de negócio. Tentativas de acesso sem permissão geram HTTP 403 e alerta na tabela auditoria_seguranca.
07 Gestão de Sessões Tokens stateless assinados no formato s2.<uid>.<token_version>.<exp>.<nonce>.<hmac_sig> transmitidos exclusivamente via cookies HttpOnly; Secure; SameSite=Strict (sem armazenamento em LocalStorage/SessionStorage), controle de versão de sessão (token_version) para revogação instantânea em logout e política de troca obrigatória de senha (must_change_password).
08 RLS (Row-Level Security) Função aplicar_rls_postgresql() executa ALTER TABLE public.<t> ENABLE ROW LEVEL SECURITY e REVOKE ALL ON TABLE public.<t> FROM anon, authenticated nas 8 tabelas do Supabase, bloqueando acesso direto pela API PostgREST pública.
09 Rate Limits (3 Níveis) Controle por IP em janela deslizante: Login (máx. 15 req/min), Uploads (máx. 20 req/min) e API Global (máx. 120 req/min), retornando HTTP 429 + bloqueio de conta por 15 min após 5 falhas de senha.
10 Validação de Inputs Schemas Pydantic v2 estritos combinados com validação de Content-Length no middleware (bloqueio automático HTTP 413 acima de 15 MB).
11 Anti-SQL Injection Uso exclusivo de queries parametrizadas do SQLAlchemy ORM em todos os routers. Nenhum input de usuário é concatenado em strings SQL.
12 Proteção Anti-XSS Sanitização server-side via sanitizar_texto_seguro() (remoção de tags HTML, caracteres de controle e atributos javascript:/on*=) + função escapeHtml() no frontend + cabeçalho Content-Security-Policy.
13 Proteção Anti-CSRF Defesa em profundidade: cookies SameSite=Strict + validação de igualdade entre cabeçalho Origin e Host em métodos POST/PUT/DELETE/PATCH + envio automático de X-Requested-With: XMLHttpRequest e X-CSRF-Token.
14 Security Headers Injeção global de Content-Security-Policy, Strict-Transport-Security, X-Frame-Options: DENY, X-Content-Type-Options: nosniff, Referrer-Policy, Permissions-Policy e Cross-Origin-Opener-Policy: same-origin.
15 Uploads Seguros Inspeção dos Magic Bytes reais do binário decodificado (assinaturas \xFF\xD8\xFF JPEG, \x89PNG, RIFF..WEBP, GIF8), teto de 10 MB, renomeação com UUIDv4 e entrega com nosniff.
16 Tratamento de Erros Handler global @app.exception_handler(Exception) que captura falhas inesperadas, grava o erro internamente com um trace_id único e retorna mensagem genérica segura sem expor stack traces.
17 Criptografia de Dados Implementação de cifra de fluxo autenticada CTR-HMAC-SHA256 (Encrypt-then-MAC) com IV aleatório de 128 bits (formato enc1.<base64>.<hmac>) para proteger snapshots em repouso + TLS 1.3 em trânsito.
18 Dependências Seguras Versões mínimas seguras fixadas em requirements.txt e eliminação de pacotes legados desnecessários.
19 Backup Automático Geração automática diária (janela de 24h) de snapshot completo criptografado na tabela backups_automaticos + endpoints para geração manual e exportação de stream binário seguro no formato .scrcbak com autenticação HMAC e hash SHA-256.
20 Monitoramento & Auditoria Dinâmica Auditoria dinâmica em tempo real (avaliando HTTPS, CORS, secrets, RLS, backups e headers) exposta em GET /api/seguranca/painel, acompanhada de telemetria contínua de eventos classificados por severidade (INFO, WARN, CRITICAL).

7. Variáveis de Ambiente, Execução Local e Deploy

DevOps & Operação

7.1. Variáveis de Ambiente Suportadas

  • DATABASE_URL: String de conexão PostgreSQL do Supabase (ex.: postgresql+pg8000://postgres.<ref>:<senha>@aws-1-sa-east-1.pooler.supabase.com:6543/postgres). Se omitida localmente, utiliza SQLite (scrc.db).
  • SCRC_AUTH_SECRET: Segredo mestre para derivação da chave HMAC-SHA256 de tokens de sessão.
  • SCRC_ENCRYPTION_KEY: Segredo mestre para derivação da chave de criptografia em repouso (CTR-HMAC-SHA256).
  • SCRC_CORS_ORIGINS: Lista separada por vírgulas de domínios adicionais autorizados no CORS.
  • SCRC_ENABLE_DOCS: Defina como 1 apenas em ambiente de desenvolvimento caso deseje habilitar /docs (Swagger UI).

7.2. Comandos de Execução e Deploy Contínuo
